# Hxv4 补丁封包：让引擎吃下补丁包的条件

本文记录**重封包**（尤其是"打补丁"场景）能被游戏引擎正常读取所必须满足的条件，
以及一套**离线自检**方法。适用对象：使用 Hxv4 变体 XP3 的 KiriKiri 游戏
（Hikari Field 等发行方的国际版，以及日版新框架那批）。

典型症状是"包明明封进去了，引擎也加载了，但资源读不出来"：轻则图不显示、不报错，
重则 TJS 抛 `Cannot convert the variable type ((void) to Object)` 并崩。

相关源码：

- `CxdecRepacker/pack_static/pack_static.cpp` —— `open_flag`、补丁修订号
- `CxdecRepacker/pack_static/enumerate.cpp` —— 条目名、域、每文件 key
- `CxdecRepacker/core/pack.cpp` —— 数据编码、条目 0 段表覆盖
- `CxdecExtractorLoader/CxdecExtractorLoader.cpp` —— 封包入口与默认输出名

---

## 0. 结论速查

| # | 条件 | 违反后的症状 | 在哪儿 |
|---|---|---|---|
| 1 | 索引条目名必须是占位名 `U+5000+序号` | 引擎按裸名找资源时命中条目名、**绕开 Hxv4 映射表**，拿不到每文件密钥 → 读出未解密的字节 → 图片解码失败 → 崩 | `enumerate.cpp` |
| 2 | 域 = 该文件**真实所属目录**的哈希（目录带结尾斜杠、小写） | 引擎按原域查不到我们的记录 → 静默不替换 | `enumerate.cpp` / 解包结果 |
| 3 | 每文件 key 建议沿用原包那把 | 自编 key 只能"自搅自解"自洽，引擎那一侧未必认 | `enumerate.cpp` |
| 4 | Hxv4 描述符 `flags` 的 bit0 必须为 0 | 引擎能挂载、映射表也解得开，但内容层解不回来 → 资源读不出 | `pack_static.cpp` |
| 5 | 补丁文件名按发行版区分 | 名字不对引擎不挂载，或被当普通档案挂载、把目录清单顶掉 | `CxdecExtractorLoader.cpp` |

**唯一的权威验收**：把**未改动**的解包目录重封一遍，与原件比 SHA256 —— 应当**完全相同**。
任何一环写歪都会立刻暴露（见第 7 节）。

## 1. 条目名：必须是占位名，不能写真实文件名

XP3 索引里每个 `File` 块的 `name` 字段，真包一律是**短 Unicode 顺序字符**（第 i 条 = `U+5000+i`）。
唯一例外是个别基准包的 entry 1 会字面写成 `startup.tjs`，这也是"记录序号要不要 +1"这条
经验的来源：`entry_base = 1 if entries[1].name == "startup.tjs" else 0`，
`xp3_entry_index = filter_flag + entry_base`（仅 `archive_slot == 0` 时成立）。
大部分包 `entry_count == record_count`，映射是 1:1；带 `startup.tjs` 的那个
`entry_count == record_count + 1`。

**写真实文件名的后果**：脚本请求的是裸名（如 `喫茶_店の前a`），引擎进入"猜扩展名"阶段，
拼成 `喫茶_店の前a.png` 去**条目名**里找；因为条目名就是真名，捷径直接命中 ——
而这条捷径**不经过 Hxv4 映射表**，也就拿不到那条记录的 `key`。
读出来的是还带着内容层变换的原始字节，图片解码失败，
`createAffineSource` 返回 void，随后对 void 取属性：

```text
trace : ... kagenvimage.tjs[(function) updateImageSource] <-- ...[(function) _setImageFile] ...
%1=(string)"喫茶_店の前a:画像がロードできません:"
        Cannot convert the variable type ((void) to Object)
        Hardware exception raised
```

**做法**：条目名写成 `U+5000 + 序号`，真名只参与计算
`file_hash = BLAKE2s-256(UTF16LE(文件名 + 盐))` —— 那才是查表用的键。

## 2. 域：必须是文件真实所属目录的哈希

```text
域 = SipHash-2-4( UTF16LE("<目录路径>/" + 盐) )      # 目录带结尾斜杠、字符串小写
根域 = 只哈希盐
```

同一款游戏里，域的取值来自运行时注册的路径（`autopath(...).toLowerCase()` 一类），
**必须按包逐个核对**，不能假定"平铺 = 根域"。

实测过的对应关系（某 Hxv4 游戏的 `data.xp3`，23 个域中反查命中 4 个）：

| 域（16 位 hex）| 目录 |
|---|---|
| `BC6792F831D5FBD5` | `system/` |
| `122C5CA31EF46C1F` | `font/` |
| `35CAB850E76B65EF` | `image/` |
| `96E4AD7DBF1C1F16` | `sound/` |

另一个包的 119 条**全部**住在根域；同一个包里的 `extra_standbg.png` 却住在
`data.xp3` 的另一个子域里。也就是说：**"平铺包一律塞根域"必然有一半场景是错的**——
碰巧住根域的文件能生效，其余静默失效。

## 3. 每文件 key：自由数据，补丁建议沿用原包的

映射表里每条记录的 64 位 `key` 是打包方自由挑的，**不是可推导公式的产物**。
实测：

- 某真包 119 条 key 与常见的 SplitMix64 序号公式：**0/119 相同**；
- 另一真包 4087 条记录只有 2704 个不同 key（同一把 key 会被多条记录复用）。

因此"自编 key"只能保证自搅自解自洽，引擎那一侧是否接受取决于实现细节。
补丁替换的都是包里已有的文件，没有理由自编：从解包清单（`.alst`）按
`(域哈希, 文件哈希)` 取出**原包那把 key** 即可。

## 4. `open_flag`：描述符 `flags` 的 bit0 必须为 0

Hxv4 描述符（14 字节）里的 `flags`，bit0 有两个作用：

- **选 nonce**：为 0 用 `nonce0`，否则用 `nonce1` 解映射表负载；
- 曾被当作"推内容层 filter 种子时要不要用 holder 常量扰动 key"的开关。

实测结论是**后半句不成立**：`flags = 1` 时，引擎**确实用 `nonce1` 解开了映射表**
（所以它查得到我们的 record），**但内容层 filter 的种子仍按 `open_flag = 0` 那套推**。
按 1 搅出来的密文，引擎按 0 解 → 全是乱的 → 资源读不出来。

对照实验（同一个包只改 flags，其余不动）：

| 包 | flags | 引擎表现 |
|---|---|---|
| 平铺补丁（原样）| 1 | 能挂载、能查到 record，资源读不出 |
| 只把 flags 改 0 | 0 | **正常显示** |

**做法**：封包侧 `open_flag` 一律 0；`build_filter_state()` 里那条按
`open_flag` 扰动 key 的分支只用于读老包，封包不要走。

## 5. 补丁文件名：按发行版区分

- **国际版**（Hikari Field 等）：只认 **`patch.xp3`**；
- **日版**新框架那批：要求带修订号的 **`patch@r<N>.xp3`**，
  且修订号需要压过游戏自身的 build 号，否则引擎当它比本体旧而跳过
  （调试时"加大数字再试"）。

名字不对时的典型表现：不是"没反应"，而是被当成**普通档案**挂载
（引擎的挂载日志里会出现它），其目录清单会把基准包同一目录的清单顶掉，
于是整个目录的资源在引擎眼里消失——同样是"不报错、但东西没了"。

## 6. 条目 0：警告占位图与它的僵尸段表

每个包的 entry 0 都是一张 1×1 的 PNG，tEXt 关键字写 `Warning`，
内容是 `Warning! Extracting this game data may infringe on author's rights.`（910 字节）。

它的 `info` 说 910 字节，**但它自己的 `segm` 说 `(offset=88, orig=157, arch=157)`** —— 自相矛盾。
实测 6 个真包（不同档案）这一条**逐字节一致**，是老布局留下的常数
（`88 = 文件头 40 + 48`），引擎不读它。

重封包要逐字节复刻原件就得连这个僵尸值一起抄：在生成条目 0 时用
`PackEntry::segments_override` 写死 `{0, 88, 157, 157}`。

## 7. 离线自检方法（不用开游戏）

### 7.1 锚点法

先解原包里一条**已知明文**的记录，与明文逐字节比。一致 ⇒ 我们的解码链 == 引擎的解码链，
后面所有离线结论才可信。（解码链 = 映射表解密 + 每文件 filter 种子推导 + 边界/取值变换。）

### 7.2 同一条记录用两种 `open_flag` 各解一次

输出两列立刻说清密文是按哪个搅的，第 4 节那个 bug 就是这么定位的：

```text
原包 entry 72     : f0=PNG    f1=???     ← 原包按 0 搅
我们的补丁 entry 1 : f0=???    f1=PNG     ← 我们按 1 搅（与引擎不一致 → bug）
```

### 7.3 逐条对比

把两份包按索引逐条比 `name` / 段表 / adler32 / 数据摘要，再比 Hxv4 映射表**密文**本身。
整体 SHA 只能回答"一样/不一样"，逐条对比能直接指出"偏在哪一条"。

### 7.4 引擎自己的现场

```text
游戏目录/savedata/krkr.console.log
```

**只在崩溃时写**（进程干净退出时没有这个文件，别以为日志丢了）。
其中的 `-- Register dump --` 与 `trace :` 两段会直接给出失败的 storage 名和调用链。

## 8. `.sig` 文件说明

每个归档旁的 `<名字>.sig` 是 212 字节文本：

```text
-- SIGNATURE - SHA256/PSS/RSA --
<base64，分行>
```

- 算法是 **RSA-PSS + SHA256**，签名 128 字节（1024 位）；
- bootstrap DLL 里只嵌了**公钥**，`System.checkSignature(file)` 默认读 `file + ".sig"`；
- 启动脚本实际只对 **exe** 和 movie plugin 调校验，**不校验 `.xp3`**；归档旁的 `.sig`
  是给发行方启动器做下载完整性用的；
- **没有私钥就无法为改动过的内容重签**。因此正确处理方式是：
  - 逐字节复刻某个归档（内容未变）→ 原 `.sig` 依然有效，直接沿用；
  - 内容改过的基准包 → 签名必然失效，且无法重签（游戏本体不受影响）；
  - 补丁包 → 不需要 `.sig`。

## 9. 已知遗留

- 平铺模式目前只能算根域。要支持"真实文件名 + 真实目录"的补丁，域需按
  `SipHash(UTF16LE("<目录>/".lower() + 盐))` 计算；但解包清单里只有 hash→hash、
  没有真目录名，所以可行路径是：**在解包目录里原地替换对应文件后整包重封**，
  或在打包目录里给出真实目录结构。
- `open_flag = 1` 那条分支目前没有任何已知可用的样本，保留只为读老包。
- `.sig` 的公钥提取与校验尚未实现。
