# 01 · 容器与索引结构

本篇讲 Hxv4 变体 XP3 的**静态结构**：文件头、索引块树、条目字段、以及那个自定义的
`Hxv4` 块放在哪。读资源名/密钥那两篇之前先看这篇。

## 1. 文件头（40 字节）

```text
偏移  长度  内容
0x00  11   魔数  58 50 33 0D 0A 20 0A 1A 8B 67 01
0x0B  8    u64 = 0x17          恒为这个值，**诱饵**，不要拿它当索引偏移
0x13  4    u32 = 1
0x17  1    0x80
0x18  8    u64 = 0            预留（读包里恒为 0）
0x20  8    u64 = 索引偏移        ★ 真正的索引位置
```

数据区从 **0x28（40）** 开始，紧接文件头。修正一点常见误读：头部读到的第一个"索引偏移"
（在 0x0B）是诱饵，照它去找索引会失败。

## 2. 索引块

索引位于 `0x20` 指向的位置，整体形态：

```text
偏移  长度  内容
+0x00 1    flag（实测 0x01）
+0x01 8    u64 压缩后长度
+0x09 8    u64 原始长度
+0x11 ...  zlib 流（解出来就是下面的 chunk 树）
```

chunk 树的头部字段用 `4 字节名字 + u64 长度 + 内容`，内容按 4 字节对齐。
结构是：**先一个 `Hxv4` 块，再逐个 `File` 块**。

### 2.1 `Hxv4` 块 = 14 字节描述符

```text
+0x00  8   payload_offset   映射表在文件中的物理偏移
+0x08  4   payload_size     加密表的大小
+0x0C  2   flags            bit0 即 open_flag，用来选解密 nonce（见 03 篇）
```

描述符之后不是明文表：这段负载是 **XChaCha20-Poly1305** 加密的。
它的明文形态与 record 布局见 03 篇。

### 2.2 `File` 块 = 一个条目

内部三个子块，顺序固定为 `adlr` → `segm` → `info`：

| 子块 | 长度 | 内容 |
|---|---|---|
| `adlr` | 4 | 明文数据的 adler32（写包时要在**变换之前**算）|
| `segm` | 28 × n | 段表，一个条目可以有多段 |
| `info` | 22 + 2n | 条目元信息 |

`segm` 每段 28 字节：

```text
+0x00  4  flags          bit0 = 该段是否 zlib 压缩
+0x04  8  offset         该段在文件中的偏移
+0x0C  8  original_size  解压后长度
+0x14  8  archived_size  存储长度
```

`info`：

```text
+0x00  4  flags          明文条目为 0x80000000（"受保护"），条目 0 为 0
+0x04  8  original_size
+0x0C  8  archived_size
+0x14  2  name 长度（字符数）
+0x16  ...name，UTF-16LE，**不含结尾 0**
```

## 3. 条目名

真包一律使用**短 Unicode 顺序占位名**：第 i 条 = `U+5000 + i`（即「倀倁倂倃…」）。

- 例外：个别基准包的 **entry 1 会字面写成 `startup.tjs`**。这类包的
  `entry_count == record_count + 1`、记录到条目序号的换算要 +1；
  其余包 `entry_count == record_count`，是 1:1。
- **不要**把真实文件名写进条目名，代价见 04 篇第 1 节。

## 4. 条目 0：警告占位图

每个包的 entry 0 都是一张 1×1 PNG（910 字节），tEXt 关键字 `Warning`，内容为
`Warning! Extracting this game data may infringe on author's rights.`。

它的字段自相矛盾，这是**原包本来就有的**，不是我们抄错：

```text
info: flags=0, original_size=910, archived_size=910
segm: flags=0, offset=88,      original_size=157, archived_size=157
```

实测多个不同档案的包，这一条**逐字节一致**（`88` = 头部 40 + 48），是旧布局留下的常数。
引擎不读它。重封包要逐字节复刻原件就得连这个僵尸值一起写（见 04 篇第 6 节）。

## 5. 一份真实包的字段速查

以某个 119 条目的档案为例：

```text
文件头 40 字节
数据区 40 .. payload_offset        每条目数据（条目 0 占前 910 字节）
Hxv4 描述符负载                    XChaCha20-Poly1305 加密的映射表
索引块（zlib 压缩）                chunk 树：Hxv4 + 119 × File
```

条目 1 的段偏移紧接条目 0 的数据，比如条目 0 占 `[40, 950)`，条目 1 就从 `950` 开始。
