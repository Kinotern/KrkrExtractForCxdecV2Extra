# 02 · 资源名与哈希

Hxv4 不存明文路径。运行时拿到一个逻辑资源名（例如 `喫茶_店の前a.png`），
要把它折算成一对哈希去映射表里查：

```text
逻辑资源名 ──┬─► file_hash    (32 字节)  ← 文件名部分
             └─► domain_hash  ( 8 字节)  ← 目录部分
                     │
                     ▼
        在 Hxv4 映射表里查 (domain_hash, file_hash) 同时相等的记录
                     │
                     ▼
        命中后：packed 低 16 位 → 条目序号；record.key → 数据层过滤器种子
```

## 1. 盐（mediaName）

两个哈希都额外拼一段**盐**。它不是固定值，来自游戏启动脚本里的 bootstrap 前缀
（含冒号时取冒号前那段，否则用默认串）。同一款游戏里它是常量，换游戏要重新确认。

我们把它存进派生参数容器（`hash_domain` 字段），封包时优先用派生产物里带的，
没有才回落默认值。**不要写死**。

## 2. file_hash

```text
file_hash = BLAKE2s-256( UTF16LE(逻辑文件名 + 盐) )        # unkeyed
```

要点：

- **用规范化之后的逻辑文件名**，通常带扩展名。裸逻辑名会算错：
  例如音频逻辑名 `bgm01`，参与计算的是 `bgm01.opus`；它的循环信息 sidecar 是
  `bgm01.opus.sli`（`.sli` 是唯一已知由主程序硬编码追加的扩展名）。
- 实现里存在 keyed 变体（密钥为派生出的 `hash_key` 前 32 字节），
  但**实测样本 key_len 为 0**，走的是 unkeyed；不能靠"hash_key 非空"来判断走哪条。
- 哈希只取**文件名**部分，不含目录。

## 3. domain_hash

```text
domain_hash = SipHash-2-4( UTF16LE(目录路径 + 盐), key = 16 个 0 字节 )
```

- 输出 8 字节，写进映射表的那 8 个字节就是它（引用时看到的十六进制串，
  例如根域 `94D4A97C61498621`）。
- **根目录 = 只哈希盐本身**。
- 目录字符串带**结尾斜杠**、且是**小写**（来自运行时的 `autopath(...).toLowerCase()`）。

实测反查某档案 23 个域，命中 4 个，可以据此理解目录的写法：

| 域 | 目录字符串 |
|---|---|
| `BC6792F831D5FBD5` | `system/` |
| `122C5CA31EF46C1F` | `font/` |
| `35CAB850E76B65EF` | `image/` |
| `96E4AD7DBF1C1F16` | `sound/` |

注意 `system`（不带斜杠）算出来是另一个值，**对不上**。反查目录名靠枚举候选
字符串比对哈希即可，这是把一个陌生包的域翻回人类可读名字的实用手段。

**关键实践结论**：域是**逐包、逐目录**的，不能假定"文件都在根域"。
同一个档案里，有的文件住根域、有的住子域；把文件塞错域，引擎按原域查不到，
表现是**静默不替换**（不报错，也不生效）。

## 4. 运行时怎么把裸名解析成条目

脚本里写的大多是裸名（`[image storage="喫茶_店の前a"]`）。引擎侧：

1. 按资源类型**猜扩展名**，逐个拼上（`.png` / `.tlg` / `.opus` …）后尝试解析；
2. 解析目标先看**索引条目名**，命中就直接用条目（这条捷径会绕开映射表，见 04 篇第 1 节）；
3. 否则按第 2、3 节算出 `(domain_hash, file_hash)` 去映射表查记录。

所以**文件名要按引擎规范化后的形态参与哈希**，而**索引条目名要保持占位名**——
这两件事看起来矛盾，其实各管一段。

## 5. 记录 → 条目序号

映射表里的记录本身不带偏移，靠序号对上索引里的条目：

```text
archive_slot = (packed >> 16) & 0xFFFF     # 实测恒为 0
filter_flag  =  packed       & 0xFFFF

entry_base   = 1 if entries[1].name == "startup.tjs" else 0
xp3_entry_index = filter_flag + entry_base        # 仅在 archive_slot == 0 时成立
```

实测的两种包：

- 条目名全是占位名 → `entry_base = 0`，`filter_flag` 就等于条目序号；
- entry 1 字面是 `startup.tjs` → `entry_base = 1`，记录序号整体 +1 才落对条目。

**封包侧只需照抄被替换档案的形态**：真包 `filter_flag` 就等于(记录下标)，
条目 0 是占位图、其后逐条 1:1 对应即可。
