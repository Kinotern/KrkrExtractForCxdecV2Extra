# 03 · 数据层：密钥与过滤器

这一层管的是"条目里的字节怎么变成文件的字节"。搞不清它，封出来的包就是
"引擎能查到、但读出来是乱码"。

## 1. 映射表（`Hxv4` 负载）本身怎么加密

```text
文件中：payload_offset 起 payload_size 字节
  +0x00  16  Poly1305 认证标签
  +0x10  ... XChaCha20 密文
```

- 算法：**XChaCha20-Poly1305**（AEAD，带 16 字节标签）；
- 密钥：32 字节 `HXV4_KEY`；nonce：24 字节，`open_flag == 0` 用 `nonce0`，否则 `nonce1`；
- 明文形态：

```text
  +0x00  4   u32 解压后长度
  +0x04  ... zlib 压缩的 TJS binary Variant 数据（域表 + 记录表）
```

记录（每条）字段：

```text
domain_hash[8]   域（写进文件的那 8 字节）
file_hash[32]    文件标识
packed  u32      高 16 = archive_slot，低 16 = filter_flag
key     u64      该条目的数据层密钥
```

**认证标签是我们自己算的**：只要拿到 `HXV4_KEY` 与两个 nonce，就能写出
"签名合法"的映射表——防篡改在这一层挡不住持有密钥的人。

## 2. 每文件 key 是自由数据

`key` 不是任何可推导公式的产物，是打包方随手挑的 64 位值。实测证据：

- 某真包 119 条 key 与常见的"序号 → SplitMix64"公式：**0/119 相同**；
- 另一真包 4087 条只有 2704 个不同 key（同一把 key 被多条记录复用）；
- 条目 0 的 key 在同一款游戏的所有档案里都一样，但换游戏就不同
  ——说明它是**按包/按游戏生成**的自由值，不是常量表项。

实践含义：

- **读包**：只用记录里存的 key，不需要知道它是怎么来的；
- **封包**：自编一把也能"自搅自解"自洽，但引擎是否与你推的一致取决于实现细节（见第 5 节）；
  替换包里已有文件时，最稳的是**沿用原包那把 key**。

## 3. 从 key 到 48 字节过滤器种子

引擎用 `key` 作为种子，跑游戏专有的 **DRIP VM** 展开成 48 字节状态：

```text
BuildFilterState(key64, open_flag):
  1. key_lo = key64 & 0xFFFFFFFF ; key_hi = key64 >> 32
     open_flag == 0 时：key_lo ^= holder[2] ; key_hi ^= holder[3]
  2. state[0x00..0x08] = drip_get64(key_lo)      # 边界种子 0
     state[0x08..0x10] = drip_get64(key_hi)      # 边界种子 1
  3. split_offset = holder[5] + (holder[4] & (key64 >> 16))
     state[0x10..0x14] = split_offset
  4. state[0x18..0x28] = 16 字节 bulk key（反复调用 drip_get64(~key_lo) 产出）
  5. state[0x2C] = 1（has_drip）、state[0x2D] = 0（null_mode）
```

- `holder[]` 是每游戏一组少量常量（实测 6 个 dword），随派生参数一起保存；
- `drip_get64(v)`：低 32 位来自对 `v` 求值某条 lane，高 32 位来自对 `~v` 求值
  ——这就是它只需要一个 32 位输入的原因。

### DRIP VM

一张 **1024 项 dword 查表** + **128 条 lane 程序**，每条 lane 是一串
`(参数, 操作码)`。操作码是加/减/乘/移位/按位组合/查表/递归一类的算术原语，
与具体游戏无关，**变的是 lane 内容与 holder 常量**。

## 4. 过滤器：四层 XOR

`FilterState(seed48)` 对条目数据施加：

1. 前 **16 字节**用 bulk key 逐字节 XOR；
2. 按 `split_offset` 把数据切成两段，各自算一套边界参数；
3. 每段内用"按字节位置**旋转**的 dword key"整段 XOR；
4. 每段在 `pos0`/`pos1` 两个位置上各 XOR 一个字节。

**全是 XOR，所以加密与解密是同一个函数**——这是离线自检能成立的基础：
我们可以拿同一个函数去"解"别人的包（见 05 篇）。

> 顺序：读取时是**先 zlib 解压、后过过滤器**（`segm.flags` bit0 决定是否解压）。

## 5. `open_flag`：bit0 只该用来选 nonce

描述符 `flags` 的 bit0 同时出现在两处逻辑里：

| 用途 | 实测结论 |
|---|---|
| 选映射表解密 nonce | **引擎确实认**：bit0=1 时它用 `nonce1` 解开了映射表（因此查得到记录）|
| 作为推过滤器种子时的"要不要用 holder 扰动 key"开关 | **不要这样用**：见下 |

对照实验（同一个包，只改 flags）：

| 包 | flags | 引擎表现 |
|---|---|---|
| 补丁包（原样）| 1 | 能挂载、能查到记录，**资源读不出来** |
| 只把 flags 改成 0 | 0 | **资源正常显示** |

结论：**内容层过滤器的种子，引擎是按 `open_flag = 0` 那套推的**。
封包侧写 `flags = 1` 时，如果同时按"1"去搅密文，引擎按"0"解 → 全乱。
所以封包一律 `flags = 0`；"按 open_flag 扰动 key"这条分支只保留给读老包用。

## 6. 文本流与压缩

- 段可以整段 zlib 压缩（`segm.flags` bit0），
  `archived_size == original_size` 时即未压缩；
- 部分文本资源带自身的一层轻薄搅动（流头 `FE FE` + mode + `FF FE`，mode 2 为 zlib
  压缩后的 UTF-16 文本）。解包器会把它解成明文，重封包时按开关决定是否搅回去；
- 条目 0（警告占位图）是**原样写出、不过过滤器**的。
