# 04 · 封包实践：让引擎认的条件

本篇是"重封包 / 打补丁"最容易翻车的一层。典型症状是**包明明封进去了、引擎也加载了，
但资源读不出来**：轻则不显示、不报错，重则脚本抛
`Cannot convert the variable type ((void) to Object)` 之后崩。

相关源码：

- `CxdecRepacker/pack_static/pack_static.cpp` —— `open_flag`、补丁修订号
- `CxdecRepacker/pack_static/enumerate.cpp` —— 条目名、域、每文件 key
- `CxdecRepacker/core/pack.cpp` —— 数据编码、条目 0 段表覆盖
- `CxdecExtractorLoader/CxdecExtractorLoader.cpp` —— 封包入口与默认输出名

## 0. 条件速查

| # | 条件 | 违反后的症状 |
|---|---|---|
| 1 | 索引条目名必须是占位名 `U+5000+序号` | 引擎走"按名字找"的捷径、绕开映射表，拿不到每文件密钥 → 读出未变换的字节 → 解码失败 → 崩 |
| 2 | 域 = 该文件**真实所属目录**的哈希（目录带结尾斜杠、小写）| 引擎按原域查不到记录 → 静默不替换 |
| 3 | 每文件 key 建议沿用原包那把 | 自编 key 只能自洽，引擎那一侧未必认 |
| 4 | 描述符 `flags` 的 bit0 必须为 0 | 引擎能挂载、表也解得开，但内容层解不回来 → 资源读不出 |
| 5 | 补丁文件名按发行版区分 | 名字不对引擎不挂载，或被当普通档案挂载把目录清单顶掉 |

## 1. 条目名：必须占位名

脚本请求裸名时，引擎会拼扩展名去**索引条目名**里找；条目名就是真名的话直接命中，
而这条捷径**不经过映射表**，于是拿不到该记录的 `key`，
读出来的是还带着内容层变换的字节。图片解码失败后，
`createAffineSource` 返回 void，紧接着对 void 取属性：

```text
trace : ... kagenvimage.tjs[(function) updateImageSource] <-- ...[(function) _setImageFile] ...
%1=(string)"喫茶_店の前a:画像がロードできません:"
        Cannot convert the variable type ((void) to Object)
        Hardware exception raised
```

做法：条目名写 `U+5000 + 序号`，**真名只参与 `file_hash` 的计算**。

## 2. 域：照文件真实所属目录

平铺（一堆真实文件名丢进一个目录）这种形态**天然只能算根域**，而目标文件可能住子域。
两种可行路径：

1. **在解包目录里原地替换**：解包结果本身就是 `域哈希/文件哈希` 的目录结构，
   把要替换的文件按大小/摘要找到、覆盖掉，再对该目录整包重封——域和 key 全是现成的；
2. 给出真实目录结构，按 `domain_hash("<目录>/".lower() + 盐)` 自己算域。

## 3. 每文件 key

替换包里已有文件时，没有理由自编：解包清单里已经记着原包那把 key，
按 `(域哈希, 文件哈希)` 取出来即可。没有清单时才退回自编。

## 4. `open_flag` 必须 0

见 03 篇第 5 节。一句话：`flags` 的 bit0 只用来选 nonce，
**不能拿它去改内容层过滤器的推导方向**，否则引擎按 0 解、密文全乱。

## 5. 补丁文件名

| 发行版 | 引擎认的名字 |
|---|---|
| 国际版（如 Hikari Field）| **`patch.xp3`** |
| 日版新框架那批 | **`patch@r<N>.xp3`**，且修订号要压过游戏自身 build 号（不生效就加大数字）|

名字不对时的表现不是"没反应"，而是被当**普通档案**挂载：它的目录清单会把基准包
同一目录的清单顶掉，于是整个目录的资源在引擎眼里消失——同样"不报错、东西没了"。

## 6. 条目 0 的僵尸段表

条目 0 的字段自相矛盾（`info` 说 910 字节，`segm` 说 `offset=88 / 157` 字节），
实测多个真包这一条**逐字节一致**，是旧布局留下的常数（`88` = 头部 40 + 48），引擎不读它。

逐字节复刻原件就得一起抄：生成条目 0 时用 `PackEntry::segments_override`
写死 `{flags=0, offset=88, original=157, archived=157}`。

## 7. 验收：逐字节复刻

**唯一权威的自检**——把**未改动**的解包目录重封一遍，与原件比对：

```text
大小相同 + SHA256 相同  ⇒  整条链正确
```

该方法能一次性覆盖：索引布局、条目名、条目 0、key、过滤器、压缩、映射表加密。
任何一环写歪都会立刻暴露。实测某 119 条目、367 MB 的档案，重封结果与原包
**SHA256 完全相同**。

更细的定位见 05 篇（逐条对比能直接指出"偏在哪一条"）。

## 8. `.sig` 文件

每个归档旁的 `<名字>.sig` 是 212 字节文本：

```text
-- SIGNATURE - SHA256/PSS/RSA --
<base64，分行（172 字符 → 解码 128 字节 = 1024 位签名）>
```

- 算法 **RSA-PSS + SHA256**；bootstrap 侧只嵌**公钥**，
  `System.checkSignature(file)` 默认读 `file + ".sig"`；
- 启动脚本实际只对 **exe** 和 movie plugin 调校验，**不校验 `.xp3`**；
  归档旁的 `.sig` 是给发行方启动器做下载完整性用的；
- **没有私钥无法为改动过的内容重签**。正确处理：
  - 逐字节复刻（内容未变）→ 原 `.sig` 依然有效，直接沿用；
  - 内容改过的基准包 → 签名必然失效且无法重签（游戏本体不受影响）；
  - 补丁包 → 不需要 `.sig`。
