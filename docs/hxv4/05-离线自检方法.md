# 05 · 离线自检方法

封包问题**不必反复开游戏试**。因为数据层的过滤器是纯 XOR（03 篇第 4 节），
读侧的解码链可以离线跑；只要拿到密钥材料，就能把任意一个包解出来对答案。

## 1. 先把解码链搭起来（前提）

用本仓库读侧的模块即可拼一个最小宿主：

- `CxdecRepacker/core/archive.*` —— 解析 XP3、找 `Hxv4`、按 `open_flag` 选 nonce 解映射表
- `CxdecRepacker/core/mapping.*` —— 记录表结构
- `CxdecRepacker/core/drip.*` —— 由 key 推 48 字节过滤器种子
- `CxdecRepacker/core/filter.*` —— 施加/撤销过滤器（同一个函数）
- `CxdecRepacker/hxv4p/*` —— 读派生参数容器，取出 `HXV4_KEY`、两个 nonce、holder、lane

流程：解映射表 → 按记录定位条目 → 读段字节 → （按需 zlib 解压）→ 过过滤器 → 明文。

## 2. 锚点法：先证明"我们的解码链 == 引擎的解码链"

**做任何离线结论之前先做这一步**，否则后面全是自说自话。

1. 找一个包，它里面有**已知明文**的文件（最方便的来源：曾经成功解包出来的文件）；
2. 用宿主解出同一条记录；
3. 与已知明文**逐字节比对**。

一致 ⇒ 解码链可信。此后：

- "我们封的包能不能被正确解开"可以用同一个宿主验证；
- "两种 `open_flag` 哪一种才对"也可以直接判定（下一节）。

## 3. 同一条记录用两种 `open_flag` 各解一次

输出两列即可定位密文是按哪个搅的。这个手法直接定位过"补丁包读不出来"的根因：

```text
原包  entry 72 : f0=PNG    f1=???     ← 原包按 0 搅
我们的补丁 entry 1 : f0=???    f1=PNG     ← 我们按 1 搅（与引擎不一致 → bug）
```

再配合"只把 `flags` 改成 0 重新封一次"的对照实验，就能确认引擎侧到底按哪一套推种子。

## 4. 逐条对比：定位"偏在哪一条"

整体 SHA 只能回答"一样/不一样"。把两份包按索引逐条比：

```text
每条：name / segm(flags,offset,orig,arch) / adler32 / 段数据摘要
另外单独比：Hxv4 映射表**密文**本身
```

这样能直接指出差异落在哪一条、是段表偏了还是数据偏了。实测用它能一眼看出
"唯一差异就是条目 0 的僵尸段表"这类问题。

## 5. 引擎自己的现场

```text
游戏目录/savedata/krkr.console.log
游戏目录/savedata/hwexcept.log          （硬件异常时）
游戏目录/savedata/Kirikiri*.dmp         （崩溃转储）
```

要点：

- **`krkr.console.log` 只在崩溃时写**。进程干净退出时没有这个文件，
  不要误以为"日志丢了"；反过来说，**没有这个文件 = 那次没崩**，这本身是重要信号；
- 里面有 `-- Register dump --` 与 `trace :` 两段，
  直接给出失败的 storage 名和 TJS 调用链，比猜快得多；
- 若启动器会**复制一份 exe 再注入运行**，日志与转储可能落在副本的目录里，
  游戏目录里看不到——排查时先确认这一点。

## 6. 常见"没有报错"的陷阱

| 现象 | 实际含义 |
|---|---|
| 资源不显示、无弹窗、无日志 | 引擎查不到记录（域写错 / 包没被挂载），属**静默失效** |
| 补丁包放进去后原来的资源也消失 | 包被当**普通档案**挂载，目录清单把基准包的顶掉了（文件名/命名规则不对）|
| 换了文件名引擎就"不吃" | 包根本没被挂载，或挂载规则与发行版不匹配 |
| 能查到记录但内容乱 | 内容层参数不一致：`open_flag`、每文件 key、段表指向 |
