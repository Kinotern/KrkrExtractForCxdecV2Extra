# 密钥管理设计

> 这份文档只为回答一件事：**同一套参数，谁产生、放哪儿、怎么找回来。**
> 现在的混乱全部来自这三件事没有分开。

---

## 1. 混乱的来源：两个写者、两种命名

| | `CxdecKeyStatic`（生成器） | `CxdecRepacker`（参数仓库） |
|---|---|---|
| 写什么 | `<exe名>_drip_program.hxv4p` | `<exe摘要>/profile.hxv4p` |
| 命名依据 | **EXE 的文件名**（stem） | **EXE 的内容摘要** |
| 谁来调 | Loader 的第 988 行 | 模块内部 |
| 写到哪 | 调用方指定（Loader 给的是 `<游戏目录>\ExtractKey_Output\Static`） | `<keysRoot>` |

两个问题：

1. **同一个游戏可能被派生两次**——Loader 跑过一次、Repacker 又自己跑一次。
2. **生成器的产物按文件名命名**——改个文件名、换个目录，就找不到之前那份了。

第 4 节的"收编"就是冲这两个问题去的：产物在游戏目录旁边，就顺手认下来，别重派生。

---

## 2. 先把三个概念拆开

| 概念 | 定义 | 谁负责 |
|---|---|---|
| **派生** | 从游戏 EXE 算出那 9 项参数 | `CxdecKeyStatic` |
| **存储** | 参数放在哪、叫什么名字 | 参数仓库 |
| **查找** | 给一个 EXE，找回它的参数 | 参数仓库 |

现在的代码把这三件事混在两个模块里，所以每次讨论都会绕回"要不要改生成器"。

---

## 3. 提议：一个仓库、按内容命名、一个写者

```
<keysRoot>/
  manifest.txt              索引：EXE 摘要 → 参数摘要 + 出处 + 时间
  <exe_digest>/             目录名 = **EXE 的内容摘要**，与文件名无关
    profile.hxv4p           参数本体
```

**命名只跟 EXE 的内容走**（这是你要求的，也是对的）：

| 情况 | 摘要 | 行为 |
|---|---|---|
| 同一个 exe 换个名字、换个目录 | **不变** | 照样命中，不重新派生 ✓ |
| 同一个 exe 内容不变、再跑一次 | 不变 | 命中 ✓ |
| exe 被改过（打补丁、重新脱壳） | **变了** | 重新派生 ✓ 这是对的行为 |

> 注意：`CafeStella.exe` 和 `CafeStella.exe.unpacked_crack.exe` 内容不同 → 摘要不同 → **会各存一份**。
> 这是刻意的：我们没法从内容判断"这两个 exe 的参数其实一样"，宁可多存一份，也不要赌。

**查找规则**（一条就够）：

```
给 EXE → 算内容摘要 → 查 manifest
  命中 → 用仓库里那份
  没有 → 派生一次 → 收进仓库 → 用
```

这样"我之前生成过"就自动被复用 ✓ —— 前提是那次生成**写进了同一个仓库**（见下一节）。

---

## 4. 那"之前生成过"的那份怎么办

关键问题：**生成器的产物没有写进仓库**，所以仓库看不见它。

三个方案：

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A** | 改 `CxdecKeyStatic`：除了现有产物，**再往仓库写一份**（按摘要命名 + 追加清单） | 从源头解决，之后永久复用 | 要动生成器；它原本不认识"仓库"这个概念 |
| **B** | 生成器不动，Repacker 派生时**先看看 exe 旁边有没有 `<exe名>_drip_program.hxv4p`**，有就收编进仓库 | 不动生成器；一次收编之后永久复用 | 得知道生成器把东西放哪了；那份文件是"按 exe 名"命名的，得靠调用者告诉我们位置 |
| **C** | 维持现状：`ImportKeyFile` 手动收编 | 最简单 | 用户得记得手动做 |

**选了 B**，理由：

- 不动已经跑通的生成器（它有自己的调用方，改了要连带改 Loader）；
- "我之前生成过"这个场景**正好是 B 的强项**——产物就在游戏目录旁边，顺手就收编了；
- 收编之后就走第 3 节的查找规则，后续全部自动。

B 的具体行为（**已实现**）：

```
派生前，先看 <exe 所在目录>\ExtractKey_Output\Static\<exe名>_drip_program.hxv4p
  有 → 收进仓库（source 记下这份文件的路径），建好 EXE 索引后直接用
  没有 → 现场派生
```

**只认同名的那一份**：同一个目录里可能躺着好几个 exe 的产物（原版、解壳版各一份），
收错了会被当成当前 exe 的参数存进仓库、之后一直错下去。名字对不上就当没有，宁可多派生一次。
文件名比较忽略大小写。

## 7. 两个当时悬着的决定，现在到哪了

1. **`keysRoot` 放哪**：**还没定**。接口上默认仍是 `"keys"`（相对当前目录）。对 Loader 来说当前目录是游戏目录 → 缓存落在游戏目录里；也可以放工具目录跨游戏共享。**我倾向工具目录**，因为参数是按 EXE 内容索引的，本来就跟游戏在哪无关。代码里原本有个 `DefaultKeysRoot()` 想替这件事拿主意，但它只有声明、从没被定义，已经删掉 —— 要定就直接定在调用方。
2. **`hash_key` 要不要参与参数摘要**：**代码里已经定了**。`CanonicalBytes` 只在 `use_keyed` 为真时才把 `hash_key` 算进去，读侧固定按 unkeyed 走。哪天真遇到用 keyed 哈希的游戏，这条要重新想。

---

## 8. 一句话总结

> **参数按 EXE 的内容摘要存放，谁派生都写进同一个仓库；查找只认内容，不认文件名。**
> 生成器不用改，只要在派生前顺手把游戏目录旁已有的**同名**产物收编进来。
